# EVTX Audit v10 — офлайн-анализ выгрузок журналов Windows для аудита КИИ / АСУ ТП

Скрипт `Audit-Evtx.ps1` читает выгруженные `.evtx` (Windows PowerShell 5.1, только
встроенный .NET), отбирает значимые для ИБ события и ищет признаки компьютерных
инцидентов: цепочки атак (эвристики и правила **Sigma**, включая корреляции Sigma v2),
подбор паролей, RDP-сеансы, ослабление защиты, очистку журналов, подключения съёмных
носителей, установку ПО и средств удалённого доступа, изменения учётных записей.
Результат — книга Excel (или два CSV, если Excel не установлен).
Журналы, учётные записи, политику аудита и политику исполнения скрипт не изменяет.

## Быстрый старт

Откройте новое окно Windows PowerShell. Скрипт не меняет политику исполнения.
Если SelfTest завершится ошибкой, основной анализ не начнётся.

```powershell
cd "C:\Users\VATukkaev\Desktop\audit script"
$ErrorActionPreference = 'Stop'
$EvtxRunner = [scriptblock]::Create(
    (Get-Content -LiteralPath '.\Audit-Evtx.ps1' -Raw -Encoding UTF8 -ErrorAction Stop)
)
try {
    & $EvtxRunner -SelfTest

    $Logs = Read-Host 'Вставьте общую папку с логами'
    $Out = Read-Host 'Вставьте папку для новых результатов'
    $RunParams = @{
        InputPath  = $Logs.Trim().Trim('"')
        OutputPath = $Out.Trim().Trim('"')
        # StartTime = '2026-09-01'                       # только период: самый сильный способ ускорить
        # SigmaRulesPath = 'D:\sigma\rules\windows\builtin' # дополнительные правила Sigma
    }
    & $EvtxRunner @RunParams
} catch {
    Write-Host 'Остановлено из-за ошибки:' -ForegroundColor Red
    $_.Exception.Message
    $_.ScriptStackTrace
}
```

Успешный SelfTest заканчивается строкой `ALL SELFTESTS PASSED — version 10.0.0`.
Удобнее всего класть выгрузку каждого компьютера в свою подпапку: связи событий
строятся только внутри одной папки и одного компьютера.

В начале запуска печатается **«Режим обработки»**: `C# (скомпилированное ядро)` —
нормальный быстрый режим; `PowerShell (совместимый)` — C#-код не удалось
скомпилировать (например, csc.exe запрещён AppLocker/EDR): анализ выполняется
полностью, но медленнее и без Sigma. Причина — на листах «Ошибки» и «Запуск».

## Листы книги

| Лист | Что в нём |
|---|---|
| **Хосты** | одна строка на компьютер: оценка риска, число КИ P1/P2, главные сценарии, срабатывания Sigma, группы мер ФСТЭК, входы и отказы, внешние IP, RDP (число и суммарное время), съёмные носители, изменения ПО, средства удалённого доступа, изменения УЗ, очистки журналов, аварийные перезагрузки, глубина журнала Security, замечания |
| **Инциденты** | кандидаты в КИ: сценарии одного компьютера с перерывом ≤ `-IncidentGapHours`; хронология, этапы атаки (тактики), УЗ, IP, Event ID, группы мер, число правил Sigma, что делать |
| **Приоритетные** | каждый сценарий (эвристика или правило Sigma) с доказательствами: оценка, MITRE ATT&CK, источник правила, меры ФСТЭК, основание связи, что проверить, ссылки на находки и Record ID |
| **Sigma** | все срабатывания правил и корреляций Sigma: тип, цепочка событий, группировка, ссылки на события, описание, ложные срабатывания |
| **Подбор_пароля** | окна отказов аутентификации (одна УЗ или spraying по многим УЗ) |
| **Входы** | сводка входов: компьютер × УЗ × результат × тип входа × источник, количество, первое/последнее время, внешний IP, коды отказа с расшифровкой (0xC000006A — неверный пароль, 0xC0000064 — нет такой УЗ, 0xC0000234 — УЗ заблокирована, Kerberos 0x18 и т.д.) |
| **RDP_итоги**, **RDP_сеансы** | суммарное время RDP по УЗ и IP; каждый сеанс с длительностью |
| **Съемные_носители** | один носитель — одна строка (серийный номер, производитель/модель, VID/PID, ёмкость), на каких компьютерах и сколько раз подключался, вероятные пользователи, запрет политикой (6423) |
| **Носители_события** | каждое событие подключения (6416, Kernel-PnP 400/410, Partition 1006, UserPnp), с вероятным пользователем: активный интерактивный/RDP-вход в момент подключения |
| **Изменения_ПО** | установка/удаление ПО (MsiInstaller 1033/1034/1035/1022), обновления Windows (19/20; обновления сигнатур — одной сводной строкой), установка служб (7045/4697) с отметкой средств удалённого доступа и признаков PsExec/Impacket |
| **Учетные_записи** | создание, включение, отключение, удаление, сброс пароля, блокировка (с компьютером-источником), переименование, членство в группах (административные, RDP, WinRM), опасные флаги UserAccountControl, встроенные УЗ Администратор/Гость |
| **Находки** | все отобранные события (технические столбцы скрыты) |
| **Сводка**, **Файлы**, **Качество_выгрузки**, **Ошибки**, **Запуск** | счётчики, обработка каждого EVTX, полнота выгрузки (какие журналы переданы, глубина Security, журналы носителей), ошибки, параметры запуска |

## Как работать с отчётом

1. **«Хосты»** (открывается первым) — какие компьютеры смотреть в первую очередь и чего
   не хватает в выгрузке (столбец «Замечания»).
2. **«Инциденты»** — по строке на кандидат в КИ. «Хронология» показывает ход атаки:
   `09:00 [P1] Отказы RDP → успешный вход → 09:02 [P1] Sigma: Создана скрытая УЗ → …`.
   «Цепочка атаки = Да» — несколько значимых сценариев **разных тактик** на одном
   компьютере; такой КИ поднимается до P1.
3. **«Приоритетные»** — отфильтруйте столбец **КИ** и пройдите строки по времени.
   P1 подсвечены красным, P2 — жёлтым; первые столбцы закреплены. Строки
   «Sigma: …» — правила и корреляции Sigma; «Источник правила» содержит ID правила.
4. По ссылкам «Находка N; файл; Record ID» (или «файл#RecordID» у Sigma) переходите
   к событию на листе «Находки» или в исходный EVTX.
5. Профильные проверки: «Съемные_носители» (сверка с журналом учёта машинных
   носителей), «Изменения_ПО» (перечень разрешённого ПО, средства удалённого доступа),
   «Учетные_записи», «Входы», «RDP_*», «Качество_выгрузки».

Все строки — **кандидаты на проверку**, а не доказанные инциденты: в «Что проверить»
указано, как подтвердить или закрыть строку.

### Что обнаруживается (лист «Приоритетные»)

| Сценарий | Оценка | Основание |

Варианты одного правила для разных журналов («… (Kernel-PnP)», «… (Partition)»,
«… (служба)», «… (Windows Installer)») объединяются в одну строку «Приоритетных»;
на листе «Sigma» они остаются отдельными.

## Правила Sigma

Движок Sigma встроен в C#-ядро: правила проверяются на тех же событиях за один проход,
без отдельного чтения журналов. События, нужные только правилам Sigma, добавляются
в XPath-запрос к Windows (с отбором по Event ID и, где возможно, по значениям полей).

**Встроенный пакет** (33 правила, 20 корреляций) нацелен на типовые инциденты
объектов КИИ и АСУ ТП:

- подбор паролей: распределённый подбор одной УЗ с разных адресов, Kerberoasting (RC4),
  Overpass-the-Hash / Pass-the-Hash (вход типа 9 через seclogo);
- удалённое выполнение и закрепление: одноразовое задание (atexec), массовая установка
  служб, изменение аудита → закрепление в той же сессии, закрепление/установка службы →
  очистка журнала Security или System, изменение времени + очистка журнала;
- учётные записи: скрытая УЗ (`имя$`), включение Гостя и встроенного Администратора,
  сброс пароля и RDP-вход под встроенным Администратором, временно включённая УЗ,
  массовое создание/удаление/отключение УЗ, RDP одной УЗ с разных адресов, явные учётные
  данные ко многим узлам;
- средства удалённого доступа (TeamViewer, AnyDesk, RMS/Remote Utilities, Radmin,
  LiteManager, VNC, Ammyy, RustDesk и др.) — служба (7045/4697) и MSI-установка;
- съёмные носители: подключение USB/WPD, диск USB/SD, запрещённое политикой устройство
  (6423), **подключение носителя → установка службы в течение 30 минут** (возможный
  перенос ВПО в изолированный сегмент);
- антивирус: повторное обнаружение угрозы после обработки, множественные обнаружения.

**Свои правила:** `-SigmaRulesPath` — файлы `.yml` или папки (рекурсивно), например
`rules\windows\builtin` из SigmaHQ. Поддерживается:

- `logsource`: product `windows`; service `security`, `system`, `application`, `sysmon`,
  `powershell`, `powershell-classic`, `windefend`, `taskscheduler`,
  `terminalservices-localsessionmanager`, `terminalservices-remoteconnectionmanager`, `wmi`,
  `driver-framework`, `codeintegrity-operational`, `firewall-as`, `bits-client`, `ntlm`,
  `smbclient-security`, `dns-server`, `kernel-pnp-configuration`, `partition-diagnostic`;
  category `process_creation` (Sysmon 1 и Security 4688 с переименованием полей),
  `ps_script`/`ps_module`, категории Sysmon;
- `detection`: выборки-словари и списки, ключевые слова, модификаторы `contains`,
  `startswith`, `endswith`, `all`, `re` (с `i`/`m`/`s`), `cidr`, `exists`,
  `gt`/`gte`/`lt`/`lte`, `windash`, `cased`; условия `and`/`or`/`not`, скобки,
  `1 of …`, `all of …`, `them`;
- корреляции Sigma v2: `event_count`, `value_count`, `temporal`, `temporal_ordered`
  с `group-by`, `aliases`, `timespan` (s/m/h/d/w), условия `gt`/`gte`, `generate`.
  Корреляции всегда считаются внутри одной папки и одного компьютера.

Не поддерживаются (правило пропускается, причина — на листе «Ошибки»): `base64`,
`base64offset`, `utf16*`/`wide`, `expand`, `fieldref`, агрегации Sigma v1 (`| count()`),
другие product. Правила категории `process_creation` заставляют читать все 4688 /
Sysmon 1 — на серверах это заметно замедляет анализ; подключайте их осознанно.
Если Windows отклонит слишком сложный запрос с селекторами Sigma, файл читается без них
(отметка на листе «Файлы»), а не полным медленным просмотром.

Необязательное поле правила `fstec239: [УПД, ОПС]` задаёт группы мер; без него группы
выводятся из тактик ATT&CK в `tags`.

## Меры приказа ФСТЭК России № 239

Столбцы «Меры ФСТЭК №239 (группы)» указывают **группы мер**, к которым относится сценарий:
ИАФ (идентификация и аутентификация), УПД (управление доступом), ОПС (ограничение
программной среды), ЗНИ (защита машинных носителей информации), АУД (аудит безопасности),
АВЗ (антивирусная защита), ЗИС (защита информационной (автоматизированной) системы и
её компонентов), ОДТ (обеспечение доступности). Это ориентир для аналитика — к какому
разделу требований относится находка, — а не вывод о (не)выполнении конкретной меры.

## Скорость

- **Отбор на стороне Windows.** XPath-запрос по провайдеру и Event ID, фильтры по типу
  входа, SID, статусу, шине диска и периоду `-StartTime`/`-EndTime`: ненужные записи
  не рендерятся и не попадают в PowerShell.
- **C#-ядро** (компилируется при запуске через `Add-Type`, оптимизированная сборка):
  разбор XML, правила, запись находок, корреляция отказов, сводки и Sigma. Результат
  совпадает с PowerShell-реализацией байт в байт (проверяется SelfTest).
- **Приоритизация без повторного чтения находок:** нужные ей строки сразу пишутся в
  небольшой `TriageInput.csv`.

Замер (PowerShell 7.4, Linux, синтетический набор из 22 800 событий, 21 000 находок):

| Этап | на событие |
|---|---|
| разбор XML в C#-ядре | ~22–29 мкс (было 75 мкс до оптимизации ядра, ~210–260 мкс в PowerShell v9.2) |
| правила + запись находки в C#-ядре | ~30 мкс (было ~96 мкс; ~230–250 мкс в PowerShell v9.2) |
| весь путь (PowerShell-цикл + ядро + Sigma + RDP) | в 7–8 раз быстрее совместимого режима PowerShell |

На Windows PowerShell 5.1 время чтения EVTX самим Windows API не измерялось; оно
не зависит от скрипта. Что ещё ускоряет: `-StartTime`/`-EndTime`, отдельные запуски
по папкам разных компьютеров в нескольких окнах PowerShell.

## Ограничения

Строки «Инцидентов» и «Приоритетных» — кандидаты на проверку, а не доказанные КИ.
Отсутствие строки не доказывает отсутствие атаки: нужны соответствующие журналы и
включённый аудит (см. «Качество_выгрузки»: какие журналы переданы и за сколько дней
охватывает журнал Security). Убранные из набора события в отчёт не попадают.

Цепочки и корреляции строятся только внутри одной папки и одного компьютера.
Эвристические цепочки не строятся через ошибки чтения, восстановленный XML, изменение
времени, загрузку ОС и очистку журнала. «Внешний IP» — всё, кроме частных, служебных и
документационных диапазонов; адрес VPN-шлюза или NAT будет внутренним.
«Вероятный пользователь» при подключении носителя выводится из входов 4624 (типы 2,
10, 11) без зафиксированного выхода — это подсказка, а не доказательство: события
носителей пишет SYSTEM. Флаги UserAccountControl расшифровываются по значениям
`OldUacValue`/`NewUacValue` события 4738.

## Что проверено

SelfTest (266 проверок) проходит в PowerShell 7.4 на Linux с параметрами по умолчанию,
с `-IncludeNoise`, `-NoCompiledEngine`, `-MaxEventId 5000 -StartTime … -EndTime …`,
`-IncludeNetworkLogons -IncludeAllErrors -DisplayTimeZone UTC -IncidentGapHours 2`.
Кроме тестов прошлых версий (разбор XML, RDP, подбор паролей, сценарии атак, Excel-раскладка):

- C#-ядро и PowerShell-путь на одном наборе событий дают байт в байт одинаковые
  находки, `TriageInput.csv`, RDP-интервалы, окна подбора пароля, сводки входов и итогов;
  быстрый разбор C# совпадает с XML-разбором (43 события), а его ручной сканер — с
  прежней regex-версией на 20 000 случайно искажённых XML (проверено отдельно);
- встроенный пакет Sigma загружается без пропусков, селекторы попадают в запрос Windows;
- сквозной сценарий (подбор RDP с внешнего IP → вход встроенным Администратором →
  скрытая УЗ → флаг AS-REP Roasting → USB-накопитель → AnyDesk (MSI и служба) →
  очистка журнала): ожидаемые срабатывания и корреляции Sigma, строки Sigma на листе
  «Приоритетные» в составе КИ P1, корректные листы «Хосты», «Съемные_носители»
  (один носитель из трёх журналов), «Изменения_ПО», «Учетные_записи», «Входы»,
  «Качество_выгрузки», порядок листов Excel и резервный CSV.

**Не проверено:** Windows PowerShell 5.1 (компиляция C#-ядра через csc.exe, чтение
настоящих EVTX через Windows API) и оформление через Excel COM — в среде подготовки нет
Windows и Excel. C#-код проверен компилятором в режиме языка C# 5 (уровень .NET
Framework 4.x). Если ядро не скомпилируется, скрипт сам перейдёт в совместимый режим.
Сначала запустите SelfTest на своей машине.
